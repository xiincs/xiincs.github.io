Agent 工程中的典型反例（demo 到生产的演进问题）

关键词：Tool、Skill、MCP

  • 手写 Agent 类、Tool 类（单例管理，样板代码泛滥） #业务
  • 手动搭建基础设施（会话持久化、上下文压缩、SSE 协议适配、HITL 框架） #基建
  • 配置硬编码（Prompt、MCP Server URL 等），无法统一管控与动态调整；缺少审计日志、版本快照与灰度机制，无法 A/B 测试或灰度发布，优化效果无法量化，风险不可控 #配置
  • Tool 与 Skill 无法动态编排 #Tool #Skill
  • MCP 每次调用工具都重新建立连接，缺乏连接池管理，高并发下易拖垮 MCP Server #MCP
  • 权限控制与审计缺失，用户身份只在 Session 层标识，没有透传至下游工具或 MCP 调用中，所有操作均以应用服务身份执行 #Tool
  • HITL 人工确认逻辑分散、不可靠 #Tool

AgentScope 体系

三层架构框架

三层能力：模型层、ReAct推理循环层、对外抽象体系层

核心模块

消息与事件、智能体、模型、上下文管理、工具、计划模式、流水线、标准作业流程、权限系统、中间件、RAG、长期记忆、工作区、实时语音智能体、终端UI、A2A协议

智能体即服务

架构、智能体团队、SOP服务、资源共享、RAG服务、工作区管理、MCP与技能中心、消息渠道、API

1-消息与事件

事件和消息是同一数据的两种视图，从事件流可以重建消息

  • 声明周期事件：智能体开始新回复、智能体完成回复、达到最大推理-执行迭代次数
  • 文本流式事件：新的文本块开始、增量文本内容到达、文本块完成（start → delta → end 模式）
  • 思考流式事件：start → delta → end 模式
  • 数据（二进制）流式事件：start → delta → end 模式
  • 工具调用流式事件：start → delta → end 模式
  • 工具结果流式事件：start → delta → end 模式
  • 模型调用事件：start → delta → end 模式
  • 人工介入事件：智能体暂停等待用户确认、智能体暂停等待外部执行、用户提供确认结果（输入事件）、外部系统提供执行结果（输入事件）
  • 一次性事件：HintBlockEvent（如卸载后台工具返回的结果，是一个内容注入机制，作为提示内容，会被智能体消费）、CustomEvent（传递与核心智能体流程无关的旁路信息，如任务进度，给外部订阅者看，不注入内容）

2-智能体运行时

无状态的推理-循环引擎
主要接口：

  • reply(inputs, structured_schema)：运行推理-行动循环并返回最终 Msg
    • inputs 参数支持：UserConfirmResultEvent（从暂停状态恢复）、ExternalExecutionResultEvent（从暂停状态恢复）、UserInterruptEvent（终止智能体）、None（继续）
  • reply_stream(inputs, structured_schema, yield_final_msg)：同上，但流式产出 AgentEvent
  • observe(msg)：将消息添加到上下文
  • compress_context(context_config, instructions)：压缩上下文

3-上下文管理

  • 上下文注入：每次调用模型时，智能体把三层内容拼接输入
    • 系统提示（基础系统提示、技能指令、on_system_prompt中间件钩子）、摘要（已压缩历史）、上下文（未压缩消息）
    • 钩子-运行时动态注入（以HintBlock形式附加，不修改系统提示，不影响缓存）：当前时间、计划任务、上下文用量、工具报错（连续n次）
  • 上下文压缩
  • 上下文卸载：把智能体从上下文移除的内容（被压缩的消息、被截断的工具输出）写入外部存储，方便通过文件工具（Read、Grep、Glob）回查。
    • 工作区卸载：sessions/{session_id}/context.jsonl、tool_result-{tool_id}.txt、data/{sha256}.png、skills/

4-工具

Glob：按文件名搜索
Grep：按文件内容搜索
Bash：执行 shell 命令、PowerShell：windows 上的对应工具

文件工具强制先读后写：Write 和 Edit 要先 Read，保证智能体总是基于最新内容进行操作。
Read 文本会使用 offset / limit 分页，返回带行号的 textBlock，图片以 base64 返回。
Edit 原理是替换文件中的精确字符串，当 old_string 找不到或不唯一时失败。

MCP (Model Context Protocol)：
有状态：传输协议 stdio 或 http，是持久会话，需要显式 connect() 或 close()
无状态：传输协议http，每次调用临时建会话，无需生命周期管理

元工具：是一种让智能体在运行时自主管理自己可用工具的工具，把工具分组，激活相关工具组，保持上下文聚焦。调用 reset_tools 来开关工具组，reset_tools 的输入 表示所有工具组的最终状态，是整体覆盖。basic 工具（Read 等）不受影响。

权限系统

五种权限模式：

  • DEFAULT：只读调用自动放行，其他全部询问用户
  • ACCEPT_EDITS：只读调用、Edit、Write 和 操作文件夹的 bash 命令 自动放行，其他询问用户
  • EXPLORE：只读
  • BYPASS：完全信任，全部放行
  • DONT_ASK：ACCEPT_EDITS 的无人值守版本，任何原来需要询问用户的全转为拒绝

5-RAG ★

  • 解析器：把原始文件拆分成若干 Section 对象，每个 Section 对应文件的一个自然边界（PDF页/PPT页/Markdown标题段/图片）
    • 文本解析器：整个文件作为一个Section，由下游切块器切分
    • PDF解析器：每页一个 Section，元信息带 page 字段
    • WORD解析器：按文档元素顺序遍历，相邻段落（含表格）合并为同一文本 Section，内嵌图片作为独立 DataBlock 读取（文本是 TextBlock）
    • PPT解析器：按幻灯片顺序遍历形状，文本、表格合并为同一Section，图片作为独立 DataBlock 读取，元信息携带 slide 幻灯片序号字段
    • EXCEL解析器：按工作表顺序读取，每张表的内容渲染为 markdown 或 json 文本，图片作为独立 DataBlock 读取，携带 sheet 字段
    • 图片解析器：将整张图片读取为一个 Section
  • 切块器：按近似 token 数进行切分，不依赖任何 tokenizer
    • 参数：块大小、重叠大小
  • 嵌入模型
  • 向量库
    • QdrantStore：基于 Qdrant，支持内存、磁盘、远程服务
    • MilvusLiteStore：基于 Milvus Lite
    • MongoDBStore：基于 MongoDB Vector Search
    • ElasticsearchStore：基于 es 稠密向量索引的实现，使用近似 kNN 检索
  • 知识库句柄：通过知识库句柄 KnowledgeBase 作为入口使用RAG，它把嵌入模型、向量数据库、Collection（用于物理隔离的表/命名空间）、metadata_filter多租户隔离配置（可选）绑定在一起，暴露接口

RAG 中间件支持两种工作模式：

  • static：每次 reply 的首次推理前，把输入消息作为检索关键词进行检索，检索结果被包装成 HintBlock 并注入上下文中
  • agentic：模型自主调用检索工具，检索关键词由模型自主给出

6-长期记忆

  • ReMe：监听智能体的对话，在每次回复后通过 ReMe 的 auto_memory 任务自动提取并写回记忆。存储形式是文件型：记忆卡片 + 检索索引。支持向量检索。
  • 控制模式：static_control（reply开始时后台检索，可能来不及注入） 和 agent_control （暴露工具，智能体自行决定何时搜索）
  • Mem0：第三方开源项目，存储形式是 Qdrant 向量存储 + historyDB（一个 SQLite 数据库文件，追踪记忆条目的历史变更）

7-Agent 整体效果进化

  • 内循环：结构化保存用户对话与操作轨迹；系统定期提炼用户偏好（喜欢用表格、喜欢简洁回答…）、Case 库（典型成功案例/典型失败案例，给外循环提供高质量数据）
  • 外循环：收集会话评价（用户点赞/点踩、反馈）、工具调用成功率、任务完成率，结合人工标注数据，驱动 Prompt 迭代和 Skill 策略迭代
  • A/B实验与灰度发布
    对 Hermes 的看法：
    以 Skill 的创建策略为例，这更多是一种随机的变化，缺乏有效的价值验证机制，很难判断新生成的 Skill 是否真正提升了系统能力。
    没有正向反馈的变化，只能称为扰动，而不是进化。
