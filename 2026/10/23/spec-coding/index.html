Spec Coding 规格驱动编码

Posted on 2026-10-23 · 603 words · 2 min read

Contents

  1. 实际价值
  2. 工作流 6 步
  3. 实战过程
  4. Apply 环节：面向测试编程（TDD）

当前的共识是，AI Coding 的真正瓶颈不在于模型的逻辑能力，而在于上下文管理的失效与开发意图的模糊。

提出：Spec Coding（规格驱动编码，SDD）

工具：OpenSpec（把模糊需求拆成清晰任务，生成 proposal、specs、design、tasks 文档）

实际价值

  • 减少返工（proposal 确定方向）
  • 适合复杂功能（tasks 分组聚焦）
  • 可审计（完整决策链记录，方便回溯）

工作流 6 步

  • Proposal 为什么做
  • Specs 具体要求是什么
  • Design 怎么做的技术决策
  • Tasks 拆解成哪些实施步骤
  • Apply 模型按 tasks 逐条实施
  • Archive 归档

实战过程

建议在项目根目录维护一套清晰的文档结构：

新项目

  1. 设计阶段：使用 AI + 设计规范 Rules，生成高保真 UI 稿 html 文件、标准的 PRD 需求描述，覆盖系统所有核心页面
  2. 项目搭建：问答式交互为主，熟悉技术栈，确定项目架构。
  3. 功能开发
  4. 细节打磨

功能迭代 ★

  1. 根据 PRD、CURRENT、ARCHITECTURE、API、AGENTS 生成某次需求对应的 requirename-date 文件夹，并补齐 require.md 和 test.md。
  2. 执行 opsx-propose，以 requirename-date 为输入，生成 proposal.md、design.md、task.md、spec.md。
  3. 执行 opsx-apply 生成代码，并依据 test.md 进行验证。
  4. 需求完成后，把对应 requirename-date 目录归档。

Apply 环节：面向测试编程（TDD）

TDD 遵循一个很经典的循环：

  • Red：先写一个一定会失败的测试，因为功能还没实现。
  • Green：写最少量代码，让测试通过。
  • Refactor：在测试保护下重构代码，优化结构，去掉冗余，但不改变其行为。
